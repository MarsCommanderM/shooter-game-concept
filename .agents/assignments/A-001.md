## Problem (verifiziert)

`stw-o3de/Docs/PerformanceBudgets/README.md`: Der STW-Logger meldet
`cpu_frame_ms=UNAVAILABLE gpu_frame_ms=UNAVAILABLE`. Damit kann kein
Performance-Gate bestehen. Gefordert sind lückenlose Frame-Samples als CSV mit
CPU- und GPU-Frame-Zeit (separat gemessen, nie aus FPS geschätzt), Draw Calls,
VRAM/RAM-Peak, ≥600 Samples im Messfenster, Summe innerhalb 5 % der Laufzeit.
Maschinenlesbare Ziele: `stw-o3de/Config/VisualForge/policy.json`.

## Auftrag

Lesen (Produktionsstand, z. B. `/teamspace/studios/this_studio/stw-production`,
nur lesen) und in der Engine unter `/teamspace/studios/this_studio/o3de-2605`:

1. Wo erzeugt STW heute `PERFORMANCE_PROFILE` / `cpu_frame_ms`? (Datei:Zeile)
2. Welche **echten** O3DE-26.05-APIs liefern:
   - CPU-Frame-Zeit (z. B. `AZ::Debug`/`AZ::Statistics`, TickBus-Zeit, `IConsole`-Stats),
   - GPU-Frame-Zeit (z. B. RHI/RPI Timestamp-Queries, `RPI::PassSystem`,
     `AZ::RHI::...Statistics`),
   - Draw Calls pro Frame,
   - VRAM (RHI Memory Statistics) und RAM (Prozess-RSS)?
   Jede API mit Header-Pfad und Zeilennummer belegen. Nichts aus dem Gedächtnis.
3. Vorschlag: eine engine-freie, testbare Sammelklasse (Muster wie
   `EnemyCollectionModel`/`MatchRulesetModel`) + dünner Engine-Adapter,
   CSV-Format (Spalten), Aktivierung per Env-Var (Gate) ohne Kosten im Normalbetrieb,
   geplante Unit-Tests, geplanter Gate-Marker, betroffene Dateien.
4. Risiken: T4-Headless-Vulkan-Eigenheiten, Timestamp-Latenz (GPU-Ergebnis
   kommt N Frames später), Unity-Build-Namenskollisionen (anonyme Namespaces
   gem-weit eindeutig), Server-Modul-Build (siehe Roadmap Abschnitt 7).
