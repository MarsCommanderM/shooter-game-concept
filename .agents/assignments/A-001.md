von `b0c3984` (`stw-o3de-worktree/stw-o3de/Project/user/log/Game.log`) zeigt,

```
PERFORMANCE_PROFILE warmup_s=30 window_s=60.013 samples=1865 frame_ms=31.989/37.560/40.998
  cpu_ms=8.501/10.661/12.055 gpu_ms=11.333/12.027/12.377 cpu_source=MainThreadCpuTime
  gpu_source=PassTimestampExtent resolution=1920x1080
```

Nur die ältere Zeile `PERFORMANCE_BASELINE ... cpu_frame_ms=UNAVAILABLE gpu_frame_ms=UNAVAILABLE`
meldet noch UNAVAILABLE. **Nicht neu bauen, was existiert.** Offene Lücken:
Draw Calls, VRAM/RAM-Peak, lückenloser CSV-Export, ≥3 Läufe, Formprüfung gegen
`policy.json`, veraltete BASELINE-Zeile. Zweiter echter Befund: Frame p95
37,6 ms (~25 fps) gegen das Ziel ≤16,67 ms, obwohl CPU p95 10,7 und GPU p95
12,0 ms sind. **Warum ist die Frame-Zeit so viel größer als CPU und GPU?**
(Vsync/Present-Wait, Headless-Xvfb, Sync-Punkte?) Das gehört in die Analyse.

Ursprünglicher Stand laut Doku: Der STW-Logger meldet
`cpu_frame_ms=UNAVAILABLE gpu_frame_ms=UNAVAILABLE`. Gefordert sind lückenlose Frame-Samples als CSV mit
CPU- und GPU-Frame-Zeit (separat gemessen, nie aus FPS geschätzt), Draw Calls,
VRAM/RAM-Peak, ≥600 Samples im Messfenster, Summe innerhalb 5 % der Laufzeit.
Maschinenlesbare Ziele: `stw-o3de/Config/VisualForge/policy.json`.

## Auftrag

Lesen (Produktionsstand, z. B. `/teamspace/studios/this_studio/stw-production`,
nur lesen) und in der Engine unter `/teamspace/studios/this_studio/o3de-2605`:

1. Wo erzeugt STW heute `PERFORMANCE_PROFILE` und `PERFORMANCE_BASELINE`
   (Datei:Zeile), wie genau werden `MainThreadCpuTime` und `PassTimestampExtent`
   gemessen, was fehlt gegenüber `policy.json`?
1b. Ursachenanalyse Frame 37,6 ms vs. CPU 10,7 / GPU 12,0 ms (nur belegen, nicht fixen).
2. Welche **echten** O3DE-26.05-APIs liefern:
   - CPU-Frame-Zeit (z. B. `AZ::Debug`/`AZ::Statistics`, TickBus-Zeit, `IConsole`-Stats),
   - GPU-Frame-Zeit (z. B. RHI/RPI Timestamp-Queries, `RPI::PassSystem`,
     `AZ::RHI::...Statistics`),
   - Draw Calls pro Frame,
   - VRAM (RHI Memory Statistics) und RAM (Prozess-RSS)?
   Jede API mit Header-Pfad und Zeilennummer belegen. Nichts aus dem Gedächtnis.
3. Vorschlag: eine engine-freie, testbare Sammelklasse (Muster wie
   `EnemyCollectionModel`/`MatchRulesetModel`) + dünner Engine-Adapter,
   CSV-Format (Spalten), Aktivierung per Env-Var (Gate) ohne Kosten im Normalbetrieb,
   geplante Unit-Tests, geplanter Gate-Marker, betroffene Dateien.
4. Risiken: T4-Headless-Vulkan-Eigenheiten, Timestamp-Latenz (GPU-Ergebnis
   kommt N Frames später), Unity-Build-Namenskollisionen (anonyme Namespaces
   gem-weit eindeutig), Server-Modul-Build (siehe Roadmap Abschnitt 7).
