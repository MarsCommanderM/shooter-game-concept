## Umfang

1. Dünner Adapter `Code/Source/Clients/STWPerformanceTelemetryAdapter.{h,cpp}`
   (Review-Korrektur 4), speist das A-002-Modell pro Tick:
   - `frame_ms` = bestehendes `deltaTime`
   - `cpu_ms` = bestehende `MainThreadCpuTime` (Korrektur 5)
   - `gpu_ms` = bestehende `PassTimestampExtent`-Logik, Frame-Versatz dokumentiert
   - `draw_calls` = `PassSystemInterface::GetFrameStatistics().m_totalDrawItemsRendered`
   - `vram_mib` = `RHIMemoryStatisticsInterface` (Aggregat im Code und im
     Evidence-Contract exakt benennen)
   - `ram_mib` = `ProcessMemInfo::m_workingSet`; Peak `m_peakWorkingSet` (Korrektur 2)
2. Aktivierung nur mit `STW_PERF_TELEMETRY=1` + `STW_PERF_TELEMETRY_CSV=<pfad>`.
   Ohne Env-Var: keine Memory-Statistik-Abfrage, keine Vektoren, kein Datei-I/O
   (Unit-Test beweist das mit Fake-Providern).
3. **Server-Build:** Adapter nur im Client-Pfad; `STWGameplay.Server` muss
   weiter bauen (MP-Gate baut ihn automatisch mit).
4. **Frame-Lücke (offener Punkt 1b aus A-001):** Diagnose-Marker
   `PERFORMANCE_FRAME_GAP` mit p95 von `RHISystemInterface::GetCpuFrameTime()`
   und, falls zugänglich, der RHI-`Present`-Statistik. Ziel: belegen, wo
   37,6 ms − max(CPU, GPU) herkommen (Present/VSync/Xvfb/Sync). Keine Fixes,
   nur Messung + Deutung mit Belegen im `done`-Bericht.
5. `PERFORMANCE_BASELINE ... cpu_frame_ms=UNAVAILABLE` durch echte Werte
   ersetzen oder die Zeile begründet entfernen (Gate prüft `PERFORMANCE_BASELINE`!
   Siehe `task.sh` Warteschleife; Änderung am Marker-Namen = `dependency` an Claude).
6. `stw-o3de/Docs/PerformanceBudgets/README.md`: veraltete UNAVAILABLE-Aussage
   korrigieren, Draw-Item-Semantik und VRAM-Aggregat dokumentieren; ebenso
   `stw-o3de/Docs/TechnicalBible/evidence-contracts.md` falls betroffen.
