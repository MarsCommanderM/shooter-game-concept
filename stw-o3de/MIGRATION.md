# STW O3DE production migration gate

## Scope and authority

This gate was evaluated from STW production commit
`744714ad7c087084a623aaf2f993a451313dc164` on
`brauny/stw-game-production`. It adds no alternate game and changes no file
under `stw-engine/`.

Until a later gate proves the required launcher, rendering, animation, and
gameplay boundaries, the only authoritative game remains native
`stw-engine/src/game/GameRuntime.cpp`. O3DE has no authority over production
gameplay at the current blocked state.

## Selected upstream

O3DE 26.05.0 is pinned at tag `2605.0`, commit
`3db6943249d8bd7960b9ed7e9aee310b7668586e`. The official release was selected
because it is the current stable release as of 2026-08-22 and documents recent
Linux toolchains while retaining Clang 14 as its minimum. See
[`O3DE_VERSION.md`](O3DE_VERSION.md) for the immutable pin and requirements.

## Fact-checked O3DE capabilities to test on the qualified host

- Atom documents PBR-oriented lighting, directional shadows, MSAA/SMAA/TAA,
  exposure/eye adaptation, Global Skylight IBL, and reflection probes. These
  are available engine capabilities, not features proven in STW.
- Atom's Linux RHI uses Vulkan. Hardware ray tracing is optional and is not a
  gate requirement.
- O3DE Scene Processing accepts `.gltf` and `.glb`, including scene data for
  skeletons and animations, but the 26.05 documentation still labels glTF
  support as in progress. The exact STW character fixture must therefore pass
  Asset Processor and runtime validation rather than being assumed compatible.
- EMotionFX provides Actor plus Simple Motion or Anim Graph components for
  skinned character playback. STW must use that pipeline rather than porting
  its custom skinning renderer.
- The Multiplayer Gem is built on AzNetworking and documents a
  server-authoritative model, entity replication, network input, prediction,
  and reliable/unreliable RPCs.
- O3DE documents `GameLauncher` as client-only, `ServerLauncher` as server-only
  and suitable for dedicated servers, and `UnifiedLauncher` for a client-hosted
  server. GPU-free execution of the eventual STW server still requires a real
  build and runtime test; it is not claimed from documentation alone.

## STW migration map

| Current STW system | Classification | Evidence and boundary |
|---|---|---|
| `GameRuntime` | PORT | Port game-state ownership and deterministic update ordering into `STWGameplay`; do not port SDL/OpenGL/frame-stream code. Legacy remains authoritative until GO. |
| `WeaponSystem` | PORT | `game/weapons/Weapons.hpp` is renderer-free weapon/ammo/reload/fire-event logic and is valuable gameplay code. Adapt types only at a tested boundary. |
| `CombatLoop` / `CombatSandbox` | PORT | `src/game/CombatLoop.*` is renderer-free, fixed-capacity player/bot combat state with deterministic tests. Replace arena collision queries with O3DE physics interfaces incrementally. |
| `FpsInput` | PORT | Preserve the input intent contract; route it through O3DE input and PhysX character movement. Do not port browser or OpenGL camera ownership. |
| `CharacterAnimationController` | PORT | Preserve Idle/Move/Fire state policy, but bind it to EMotionFX motion/Anim Graph assets instead of the custom runtime. |
| `RuntimeModelInstance` | REPLACE | O3DE entities, Actor/EMotionFX and Atom own model, pose, palette and draw submission after GO. |
| Custom glTF loader | REPLACE | Use O3DE Scene Processing and Asset Processor. Validate current glTF assets because upstream marks glTF support in progress. |
| Custom OpenGL renderer | REPLACE | Atom is the migration objective; do not embed `renderer_gl.cpp` in O3DE. |
| `GameplayPresentation` / `GameAudio` | DEFER | Preserve gameplay events first; select factual O3DE presentation/audio components only after the core launcher gate passes. |
| `.stwc` cache | REPLACE | O3DE Asset Processor becomes the O3DE-side asset pipeline. Keep `.stwc` only for the unchanged legacy game during migration. |
| Source assets | KEEP | Keep repository-owned source assets, but process them through O3DE and record any conversion; do not copy third-party copyrighted assets. |
| Deterministic C++ tests | KEEP / PORT | Keep behavior tests for weapons, input, combat and animation-state policy. Port them with gameplay, independent of Atom. |
| Playtest bridge | DEFER | Do not port FrameCapture, Node process control, nginx, or browser streaming during the native desktop gate. |
| Mobile web input | DEFER | Browser remains legacy transport only; no second browser game or duplicated gameplay. |

## Single-authority migration boundary

1. Before GO, `stw-engine/` is authoritative for every production subsystem.
2. The O3DE gate may contain only isolated proof code and assets; it does not
   receive production features.
3. After GO, migrate one gameplay subsystem at a time and mark its authority in
   this document. Stop extending the replaced legacy implementation once the
   O3DE version is verified.
4. Renderer, animation rendering, asset processing, and physics are replaced by
   O3DE facilities rather than maintained in parallel.
5. Browser/mobile transport stays deferred until native desktop and networking
   foundations are accepted.

## Qualified-host continuation procedure

Use a workstation that passes `Scripts/verify-host.sh`, with a real Vulkan GPU,
at least 100+ GiB free for the source workflow (substantially more preferred),
and enough RAM to limit parallel builds safely.

1. Clone the official engine outside the STW repository and detach at the pin:

   ```bash
   git clone --branch 2605.0 https://github.com/o3de/o3de.git /opt/o3de-2605
   git -C /opt/o3de-2605 rev-parse HEAD
   ```

   The second command must print
   `3db6943249d8bd7960b9ed7e9aee310b7668586e`.

2. Run the official bootstrap and register that engine:

   ```bash
   cd /opt/o3de-2605
   python/get_python.sh
   scripts/o3de.sh register --this-engine
   ```

3. From the repository root, generate the project and Gems with the pinned CLI
   rather than copying templates manually:

   ```bash
   /opt/o3de-2605/scripts/o3de.sh create-project \
     --project-path "$PWD/stw-o3de/Project" --project-name STW
   /opt/o3de-2605/scripts/o3de.sh create-gem \
     --gem-path "$PWD/stw-o3de/Gems/STWCore" --gem-name STWCore
   /opt/o3de-2605/scripts/o3de.sh create-gem \
     --gem-path "$PWD/stw-o3de/Gems/STWGameplay" --gem-name STWGameplay
   /opt/o3de-2605/scripts/o3de.sh register \
     --external-subdirectory "$PWD/stw-o3de/Gems/STWCore" \
     --external-subdirectory-project-path "$PWD/stw-o3de/Project"
   /opt/o3de-2605/scripts/o3de.sh register \
     --external-subdirectory "$PWD/stw-o3de/Gems/STWGameplay" \
     --external-subdirectory-project-path "$PWD/stw-o3de/Project"
   ```

4. Inspect the generated manifests before adding code. Configure and build the
   documented launcher target:

   ```bash
   cmake -S stw-o3de/Project -B stw-o3de/Project/build/linux \
     -G "Ninja Multi-Config"
   cmake --build stw-o3de/Project/build/linux \
     --target STW.GameLauncher Editor --config profile -j 4
   ```

5. Use the generated project and Editor/Asset Processor to create exactly one
   arena level with Atom PBR materials, directional lighting/shadows,
   environment lighting, exposure, and a sky/background. Build and run
   `STW.GameLauncher`; capture frames only from that executable.
6. Add one collision-aware FPS controller using the factual O3DE Input, Camera,
   and PhysX character-controller facilities present in the generated build.
7. Process one repository-owned or clearly permissive glTF/GLB actor through
   Asset Processor. Prove mesh, material, skeleton and looping motion through
   EMotionFX in `STW.GameLauncher`.
8. Add only player state, health and input abstraction to the generated
   `STWGameplay` Gem, with unit tests. Do not port the legacy renderer.
9. Enable and configure AzNetworking/Multiplayer using the pinned engine. Build
   the generated project's factual `GameLauncher` and `ServerLauncher` targets,
   then run one server plus two clients and verify independent replicated
   transforms, authoritative server state, disconnect and reconnect.
10. Run the server launcher without a presentation device and confirm the
    final STW server dependency graph contains no client rendering dependency.

Only actual output from these steps can change the gate decision to GO or
NO-GO.

## Decision evidence

O3DE is architecturally promising for the requested renderer, animation,
physics, asset, and multiplayer replacement. This machine cannot create the
real project, build or launch it, process assets, render Atom output, exercise
an FPS controller, validate the character, or run the two-client network proof.
There is therefore no evidence yet that O3DE is materially stronger for this
specific STW production workload in operation.

BLOCKED — requires a real GPU/build host before decision
